# 팀 피드백 반영·실제 배포 연결 계획

상태: **초기 계획 기록 — 작성 이후 팀의 실제 배포·설정·DB 감지 코드가 main에 반영됨**

아래 현재 상태/미구현 설명은 계획 작성 시점의 기록입니다.
최신 저장소별 구현 현황과 남은 연결은 [INTEGRATION.md](./INTEGRATION.md)를 기준으로 확인합니다.

기준: 팀 피드백 4개, 현재 `lily-frontend`, GitHub 조직의 빌더·CI/CD·온프레미스·DB 프로비저너 `main` 코드.
코드 확인과 운영 배포 검증은 구분합니다. 원격 API 호출로 실제 배포를 실행하지 않았습니다.
이번 문서는 태스크·담당·의존성·완료 기준을 정리합니다. 애플리케이션 동작은 변경하지 않습니다.
현재 동작 계약은 [API.md](./API.md), 운영 연결 참고는 [README](../README.md#인프라-연동-검토)입니다.

팀이 이미 수정한 기능을 재사용합니다. 조직 제한 제거와 Dockerfile 자동 생성을
이 저장소에서 새로 구현할 일로 취급하지 않습니다. 아래 태스크는 연결과 미지원 부분 보완에 초점을 둡니다.

### 추가로 발견한 제약

- `projects`의 `UNIQUE(owner_id, repo)` 때문에 같은 사용자가 같은 레포의
  프런트엔드와 백엔드를 두 앱으로 등록할 수 없습니다.
- `POST /api/projects/:id/deployments`는 현재 본문 `{}`만 받고 `queued` 기록만 생성합니다.
  외부 실행기로 작업을 전달하지 않습니다.
- 공개 랜딩의 `useDeploy`는 시뮬레이션이며 실제 배포 시작 버튼·실시간 상태 수신은 없습니다.
- 배포 기록에는 전체 상태만 있습니다. 단계·진행률·서비스 URL·실행기 job ID·커밋 SHA는 없습니다.
- SMTP 오류가 가입 API 실패인지 메일 전달 실패·미인증 로그인 차단인지는 배포 환경 로그로 확인해야 합니다.
  현재 코드에서는 메일을 응답 후 작업으로 보내고, 이메일 미인증 계정의 로그인을 차단합니다.

  Next.js가 프로젝트 UUID와 외부 build ID/앱 키를 매핑해 권한을 확인하고 내부 API 호출을 감싸야 합니다.

## 2. 구현 방향과 확정할 항목

### 인증: 별도 사용자 아이디·비밀번호 로그인, 이메일 인증 생략

**작업안:** 이메일 인증을 가입·로그인의 필수 조건에서 제거하고 실제 DB 계정·비밀번호 해시·세션은 유지합니다.
SMTP 미연결 때문에 가입·프로젝트 등록이 막히지 않도록 합니다.

- **사용자 확정: 이메일과 별개의 사용자 아이디(`username`)를 사용합니다.**
  로그인 입력은 아이디·비밀번호이며 이메일을 아이디로 취급하지 않습니다.
- 아이디 규칙 초안은 3~30자의 영문·숫자·`_`·`.`이며 소문자로 정규화해 중복을 검사합니다.
  표시 이름은 별도입니다. 가입 시 아이디를 확정하고 초기 버전에서는 변경 기능을 제공하지 않습니다.
- 기존 사용자의 UUID·프로젝트·비밀번호를 유지합니다. 전환 기간에는 기존 이메일 로그인으로
  본인 계정을 확인한 뒤 계정 화면에서 아이디를 직접 지정하게 합니다. 이메일 앞부분을 임의로 아이디에 배정하지 않습니다.
- 예시 정책 변수 `AUTH_REQUIRE_EMAIL_VERIFICATION=false`를 서버에서 읽고 UI에는 필요한 정책만 전달합니다.
  변수명·기본값은 T20에서 확정합니다. 현재 구현된 환경 변수가 아닙니다.
- 가입 후에는 로그인 페이지로 안내합니다. SMTP 없는 가입에 자동 로그인은 필수로 추가하지 않습니다.
- 서버 인증 설정뿐 아니라 `requireUser`, 프로젝트 페이지의 `emailVerified` 가드도 같은 정책을 사용합니다.
- 인증을 생략해도 `emailVerified=true`로 조작하지 않습니다. 미인증은 실제 상태로 남기고 접근 정책을 바꿉니다.
- SMTP가 없으면 인증 메일·메일 기반 비밀번호 찾기는 비활성화하고 사실에 맞는 안내를 표시합니다.
  로그인 후 현재 비밀번호를 이용한 변경은 유지합니다. 실제 발송 없이 “메일 발송 완료”로 표시하지 않습니다.
- 기존 미인증 계정도 동일 정책으로 로그인할 수 있게 합니다. 기존 세션·계정 데이터는 삭제하지 않습니다.

인증 해제는 사용자별 프로젝트 소유권 검사·세션·변경 요청 Origin 검사를 해제하는 작업이 아닙니다.
기존 인증 라이브러리의 [username 플러그인](https://better-auth.com/docs/plugins/username)은
아이디 로그인을 제공하지만 기본 가입 API에는 여전히 이메일이 필요합니다.
**별도 아이디 채택과 가입 화면의 이메일 입력 제거는 별개 변경입니다.**
T20에서 이메일을 연락처로 받을지, 이메일 없는 가입을 지원하도록 가입 API·인증 계층까지 바꿀지
확정합니다. 라이브러리 설정 하나로 두 변경이 모두 끝난다고 계획하지 않습니다.
설정 근거: [Better Auth 이메일·비밀번호 인증](https://better-auth.com/docs/authentication/email-password).

### 배포 단위: 한 프로젝트는 하나의 배포 앱

기존 프로젝트 UUID를 유지하면서 **프로젝트 하나를 배포 앱 하나**로 정의합니다.
같은 레포를 `frontend`와 `backend` 앱으로 각각 등록하고 각자 설정·환경 변수·배포 기록을 관리합니다.
복수 서비스를 한 요청으로 일괄 배포하는 Compose 기능은 별도 범위입니다.

- 앱마다 `repo`, 표시 이름 `name`, 내부 앱 키 `appName`, `branch`, `rootDir`, 포트와 배포 설정을 갖습니다.
- 레포만 같다는 이유로 중복을 거부하지 않습니다. 초기안은 계정 안에서 앱 이름 중복을 검사하는 것입니다.
  기존 이름 중복 데이터가 있는지 먼저 조회해 충돌 처리 후 새 제약을 적용합니다.
- 표시 이름을 컨테이너·Nginx 설정 파일 경로에 그대로 쓰지 않습니다. 프로젝트 UUID에서 생성한 안정적인
  내부 `appName`을 저장해 빌더에 보냅니다. `appName`은 최대 55자의 소문자·숫자·하이픈 규칙을 따릅니다.
  다른 사용자의 같은 표시 이름이 같은 Ingress·DB·슬롯을 가리키지 않게 합니다.
- 프런트엔드와 백엔드가 서로 통신하도록 각 서비스 URL과 환경 변수를 설정할 수 있게 합니다.
  서비스 URL 발급·Nginx 라우팅은 실행기/인프라 담당, 설정 입력·표시는 UI/API 담당입니다.

### API 경계: 현재 서버에서 외부 실행기로 연결

브라우저는 현재와 같이 같은 출처의 Next.js `/api`를 호출합니다.
Next.js 서버가 세션·소유권을 확인하고 외부 배포 백엔드에 서버 인증으로 요청하는 연결 모듈을 둡니다.

- 사용자 인증·계정·프로젝트 소유권은 현재 서버에서 처리합니다.
- 배포 작업 접수·빌드·기동·Nginx 연결은 팀 배포 백엔드/실행기에서 처리합니다.
- 서버 연결 모듈에서 필드명·오류·job ID·상태를 변환합니다. 브라우저에 실행기 키를 전달하지 않습니다.
- 외부 백엔드의 상태를 기준으로 실제 결과를 표시합니다. 이 저장소에 독립적인 배포 엔진을 중복 구현하지 않습니다.
- 현재 빌더는 비동기 접수 후 build ID를 반환합니다. 새 실행 엔진은 만들지 않고 이 접수를 재사용합니다.
  Next.js 기록 생성과 요청 전달에는 발송 대기 항목/재시도 연결을 추가합니다. 빌더의 접수 API에는
  현재 `Idempotency-Key` 계약이 없으므로 응답 유실 후 안전한 재시도·요청 ID 지원을 T26에서 보완합니다.

## 3. 실제 빌더 계약과 추가 확장

현재 프런트의 `repo`·`name`만으로는 빌더 요청을 구성할 수 없습니다. 서버에서 아래 실제 필드로
변환합니다. 새 프런트 API는 T21에서 확장합니다. **아래 필드를 현재 `/api/projects`에 보내면 거부됩니다.**

| 빌더 필드                       | 현재 실제 계약                                                        | UI·추가 작업                                                             |
| ------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `repoUrl`                       | 전체 `https://github.com/owner/repo` 주소, 필수                       | 입력을 정규화한 뒤 전체 URL로 변환. 조직 제한 없음                       |
| `appName`                       | 소문자·숫자·하이픈, 처음/끝 영숫자, 최대 55자                         | 표시 이름과 구분한 안정적인 내부 앱 키. 사용자별 충돌 방지               |
| `branch`                        | 생략 시 `main`                                                        | 초기 UI에 main 기본값을 명시하고 수정 가능. 기본 브랜치 자동 선택은 확장 |
| `rootDir`                       | 빈 문자열은 레포 루트, 소스 탐지·빌드 위치                            | 레포 안의 하위 앱 경로 입력. 실제 경로 검증                              |
| `targetPort`                    | 1~65535, 생략 시 EXPOSE 탐지 후 8080                                  | 내부 포트 입력/자동 선택. 호스트 포트와 구분                             |
| `database`                      | 생략/빈 값은 미사용, `postgres`·`mysql`·`auto`                        | DB 미사용·자동·PostgreSQL·MySQL 선택, JWT 앱의 DB 설정 요구 대응         |
| `readinessPath`, `livenessPath` | 개별 HTTP 경로 또는 `tcp`; 생략 시 탐지 정책                          | 경로 둘을 구분. HTTP/TCP/자동 선택과 차이 안내                           |
| `canaryPath`                    | 선택, 미지정 시 readiness 기반                                        | canary 요청을 보낼 실제 API 경로. TCP 검사와의 조합은 팀 계약 확인       |
| `env`                           | 문자열 키→값 맵, 컨테이너 전달. 공개 접두사 변수는 빌드 인자로도 전달 | 키/값 입력·비밀값 관리. 사용자 지정 build/runtime 범위는 별도 확장       |
| `token`                         | 비공개 레포 GitHub 토큰, 선택                                         | 쓰기 전용 입력, 서버 비밀 저장소 참조에서 복원해 서버 간 전달            |
| `migrationsPath`                | **rootDir 기준** SQL 폴더, 기본 `src/main/resources/db/migration`     | `migrate` 스위치와 경로 입력. ORM 명령과 혼동하지 않음                   |
| `migrate`                       | 생략 시 true, false는 플랫폼 마이그레이션 수집 생략                   | 플랫폼 SQL 실행/미사용을 명시. 앱 자체 수행 방식은 별도 확인             |
| `host`, `standby`               | 고급 내부 필드, Ingress 호스트·버스팅 대기                            | 초기 일반 폼에서는 제외. 서비스 주소와 버스팅 정책은 인프라 담당         |

예시: 모노레포의 백엔드 앱을 빌더에 보내는 **서버 간 요청**입니다. 앱 키는 서버가 소유 프로젝트로 결정합니다.

```json
{
  "repoUrl": "https://github.com/owner/product",
  "appName": "lily-project-key",
  "branch": "main",
  "rootDir": "apps/api",
  "targetPort": 8080,
  "database": "postgres",
  "readinessPath": "/health",
  "livenessPath": "/health",
  "env": {},
  "migrate": true,
  "migrationsPath": "src/main/resources/db/migration"
}
```

비밀값은 문서 예시·조회 응답에 넣지 않습니다. UI의 환경 변수 행은 서버에서 `env` 맵으로 변환합니다.
빌더 필드와 다르게 `port`, `healthCheckPath`, `githubToken`, `migrationPath`로 임의 전달하지 않습니다.

### 현재 API에 없는 확장

- **독립 `buildContext`:** rootDir 밖 공통 패키지가 필요한 workspace 지원. 빌더·온프레미스 양쪽의
  컨텍스트/소스 읽기/Dockerfile 경로 정책을 같이 바꿉니다.
- **`dockerfilePath`:** 현재는 rootDir 안 `Dockerfile`을 사용합니다. 다른 파일명 지정은 별도 계약으로 추가합니다.
- **환경 변수 범위·빌드 시크릿:** 현재 공개 접두사 필터와 임의의 범위 선택은 같은 기능이 아닙니다.
  UI가 지원하지 않는 기능을 실행되는 것처럼 표시하지 않습니다.
- **`migrationCommand`:** 현재 플랫폼은 Flyway SQL 방식입니다. Prisma·Django 등은 앱 시작/별도 작업 방식부터
  확인하고 필요하면 새 실행 계약을 만듭니다. SQL 경로 칸에 명령을 넣지 않습니다.

`rootDir`은 레포 루트 기준이고 `migrationsPath`는 **앱 rootDir 기준**입니다.
예: rootDir=`apps/api`, migrationsPath=`db/migration`이면 실제 위치는 `apps/api/db/migration`입니다.
추가할 buildContext·Dockerfile 경로는 레포 루트 기준으로 합의하고 라벨에 표시합니다.
절대 경로·레포 밖 이동·링크를 통한 이탈을 서버·실행기에서 검증합니다.
Docker `COPY`의 파일 범위는 [빌드 컨텍스트](https://docs.docker.com/build/concepts/context/)로 결정됩니다.

### 환경 변수·비공개 레포 자격 증명

- JWT 비밀키·DB 비밀번호·GitHub 토큰은 서버에서 암호화 저장하거나 비밀 저장소에 보관합니다.
  암호화 키는 DB와 별도로 운영 환경에서 관리합니다.
- 조회 응답은 키·범위·설정 여부만 반환하고 기존 비밀값은 반환하지 않습니다.
  UI에서 마스킹 문자를 실제 값으로 다시 저장하지 않습니다. 유지·교체·삭제 요청을 구분합니다.
- 실행기에 필요한 비밀값은 인증·접근이 제한된 서버 간 경로에서 전달하고 일반 목록·꽃 진입 응답에서 제외합니다.
- 실행기 로그·오류·큐의 일반 메타데이터에 원문 비밀값을 남기지 않습니다.
- 빌드 변수와 실행 변수는 분리하는 확장을 계획합니다. 현재는 env 맵과 공개 접두사 필터만 지원합니다. `NEXT_PUBLIC_*`는 브라우저 번들에 포함될 수 있으므로
  JWT 비밀키를 넣지 않습니다. 필요한 빌드 비밀값은 실행기 빌드 시크릿으로 전달하고 이미지에 남기지 않습니다.
- 환경 변수·토큰 크기에 맞춰 최대 개수·키/값 길이를 정합니다. 현재 JSON 제한 16KiB를
  그대로 쓸지 별도 설정 경로의 제한을 바꿀지 API·Nginx 양쪽에서 맞춥니다.

Next.js 빌드 환경 변수의 동작은 [공식 환경 변수 가이드](https://nextjs.org/docs/app/guides/environment-variables)를 참고합니다.

### T19 — 계약부터 맞추기

- 위 커밋의 계약을 기준으로 배포된 빌더 버전·내부 서비스 URL·인증/접근 정책을 확인합니다.
- 현재 Next.js DB의 배포 UUID와 외부 build ID를 구분하고 프로젝트 소유권과 내부 앱 키를 함께 매핑합니다.
- 초기 연결은 빌더 `GET /api/builds/:id` polling을 사용합니다. 현재 callback 이벤트 API는 기존 연결점으로
  남기고, polling 결과와 충돌하지 않게 상태 변경 기준을 하나로 정합니다.
- 입력 오류를 필드별로 반환하고, 인증·GitHub 권한·빌드·헬스체크 실패를 구분합니다.
- 첫 지원 런타임·Dockerfile 템플릿과 브랜치 기본값·포트·마이그레이션 실행 방식·서비스 URL을 확정합니다.

### T20 — 아이디 로그인과 계정 전환

- 변경 위치: `lib/auth/server.ts`, `client.ts`, `types.ts`, `session.ts`, 인증 Route Handler·요청 제한,
  인증 DB 마이그레이션, `lib/api.ts`, `app/page.tsx`, `AuthForm`, 로그인·가입 페이지,
  `AccountForm`, 메일 복구 화면·링크와 인증 오류 안내.
- `username`의 DB 고유 제약과 서버 검증을 추가합니다. 세션 응답·내 계정에서도 아이디와 표시 이름을 구분합니다.
- 아이디 로그인 API·클라이언트를 연결하고 아이디별 로그인 제한을 적용합니다.
  기존 이메일별 제한만 남겨 새 로그인 경로가 제한을 우회하지 않게 합니다.
- 기존 계정에는 충돌 없는 아이디 선택 경로를 제공합니다. 기존 UUID·소유 프로젝트를 새 계정으로 복제하지 않습니다.
- 가입 이메일 입력 정책은 라이브러리 가입 계약과 함께 확정하며, SMTP 발송은 어떤 가입 방식에서도 필수로 두지 않습니다.
- SMTP 미설정 환경에서 가입·로그인·프로젝트 등록·꽃 진입 권한 판단이 일관되어야 합니다.

### T21~T23 — 폼·저장·비밀값을 한 계약으로

- 기존 `projectSchema`와 `updateSchema`는 strict이므로 서버 변경보다 먼저 필드를 보내지 않습니다.
- 기존 프로젝트는 rootDir 미지정(빌더 요청은 빈 문자열), branch=`main` 등 실제 빌더 기본값에 맞춥니다.
  포트 등 추정할 수 없는 필드는 배포 전에 보완하도록 안내합니다.
- 배포 요청 시 설정·비밀값 버전 참조를 고정합니다. 배포 중 설정을 수정해도 진행 중 작업이 바뀌지 않습니다.
- UI는 기본 설정과 고급 설정으로 나누고 각 경로의 기준을 라벨에 적습니다.
  실제 저장 성공과 GitHub 접근·빌드 성공을 구분합니다.

### T24 — Dockerfile 자동 생성 범위

1. 선택한 브랜치·커밋과 앱 경로에서 명시된/기본 Dockerfile을 찾습니다.
2. 파일이 있으면 해당 파일을 사용합니다. 파일이 있는데 빌드가 실패했다고 자동 덮어쓰지 않습니다.
3. 파일이 없으면 팀의 기존 DockerfileGenerator 판별 결과를 사용합니다. 지원 런타임과
   실제 생성 파일의 동작을 연결하고 workspace 미지원 조합은 보완합니다.
4. 지원하는 조합만 템플릿으로 생성해 작업 공간에서 빌드합니다. 사용자 레포에 자동 커밋하지 않습니다.
5. 판별이 모호하거나 지원하지 않는 앱은 Dockerfile 제공 또는 지원 설정 선택을 안내합니다.

API 응답·로그에 `repository`/`generated` 같은 Dockerfile 출처와 적용 경로를 전달합니다.
프런트엔드가 브라우저에서 Dockerfile을 생성·빌드하는 구조로 만들지 않습니다.
이 앱은 빌드 단계에도 DATABASE_URL·인증 URL·인증 비밀키를 요구하지만 현재 생성 템플릿은
공개 변수만 ARG로 전달합니다. 실행용 env만 채워도 빌드가 완료된다고 가정하지 말고, 빌드 설정을
런타임까지 미루는 코드 개선 또는 실행기의 빌드 시크릿 계약을 T24에서 함께 결정합니다.

### T26~T28 — 실제 실행과 결과 표시

- 현재 공개 시연은 시연으로 유지합니다. 실제 배포는 로그인한 앱의 설정 화면에서 시작합니다.
- 실행기 상태에 없는 카나리·에러율·트래픽 전환 단계를 타이머로 완료 처리하지 않습니다.
  빌더의 실제 stage를 사용하고 첫 배포의 canary skipped·온프레미스 단계 생략도 그대로 표시합니다.
- 현재 플랫폼의 Flyway V/U SQL 규칙을 사용합니다. Node ORM 등 다른 실행 도구는
  별도 명령·작업 디렉터리 계약을 확장하거나 앱 자체 마이그레이션 방식으로 연결합니다.
  실패·타임아웃 처리와 실행 중복 방지는 실행기에서 담당합니다.
- 마이그레이션 성공·컨테이너 기동·헬스체크 통과·실제 라우팅 완료 후 `succeeded`를 기록합니다.
  실패한 새 버전을 성공으로 표시하지 않고 기존 서비스 유지/복귀 결과를 함께 전달합니다.
- CI/CD에는 V/U SQL 스키마 롤백·PARTIAL 결과 처리가 있습니다. 앱 컨테이너 롤백과 DB 복구 성공을
  구분하고 기존 정책을 재사용합니다. 이 프런트의 `scripts/migrate.ts`·`001-projects.sql`은
  플랫폼의 Flyway V/U 폴더와 바로 호환되지 않으므로 프런트 운영 DB 마이그레이션은 별도 배포 단계로 둡니다.
- 최신 상태를 다시 확인해 성공한 본인 프로젝트만 기존 꽃술 확대 연결점을 사용합니다.
  대시보드 UI·외부 SSO는 기존 별도 범위를 유지합니다.

상태 변환은 `QUEUED → queued`, `BUILDING/DEPLOYING → running`, `SUCCEEDED → succeeded`,
`FAILED → failed`, `ROLLED_BACK → rolled-back`입니다. 빌더 응답의 stage는 단계 표시용이며
정밀한 단계 내부 진행률은 제공하지 않습니다. 타이머로 실제 진행률을 만들어 표시하지 않습니다.
첫 조회에서 종료 상태를 받거나 canary가 running에서 바로 ROLLED_BACK으로 끝날 수 있으므로,
현재 이벤트 API의 전환 규칙을 그대로 적용하지 않고 검증된 외부 상태 반영 경로를 확장합니다.
늦은 polling 응답으로 종료 상태가 running으로 돌아가지 않게 합니다.

## 5. 실행 순서와 병행 가능 범위

1. **T19 계약 확인**, 동시에 **T20 인증 차단 해소**를 우선합니다.
2. **T21 DB·API → T22 비밀값 → T23 폼** 순서로 현재 저장소를 변경합니다.
3. 팀은 **T24 기존 Docker 자동 생성 연결·미지원 부분 보완**, **T25 제한 해제의 연동 확인**을 진행합니다.
4. **T26 실제 요청 연결 → T27 실행·Nginx·헬스체크 → T28 상태와 꽃 연결**을 진행합니다.
5. **T29 인수인계**에서 확인 결과와 남은 외부 작업을 정리합니다.

순차 진행 시 T19→T20→…→T29를 따릅니다. 팀 역할 간 병행은 계약이 확정된 작업만 진행합니다.
이 저장소의 각 구현 태스크를 마친 뒤 다음 태스크 전에 커밋합니다.
실행기 태스크는 해당 저장소의 변경과 커밋을 연결해 기록합니다. 이 계획은 변경 구현·push 지시가 아닙니다.
