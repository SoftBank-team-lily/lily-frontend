## 성능

Chromium 로컬 실행에서 180개 프레임 간격을 측정했습니다. 중앙값 16.7ms, p95 16.8ms, 평균 약 59fps였습니다. 개발 모드와 headless 브라우저에서 측정한 값이며 기기별 성능 보장은 아닙니다.

실제 브라우저의 꽃 입자는 데스크톱 약 46,400개, 모바일 약 29,400개입니다. 먼지는 각각 1,400개·600개입니다. 꽃 입자 수는 난수에 따라 조금 달라집니다. 모바일 여부는 씬 생성 시 한 번 판정해 원본과 동일하게 유지합니다.

## 기준 문서와 구현의 차이

- `.git/` 입력: 원본은 `.git` 제거 후 끝 `/`를 제거하므로 `o/r.git/`가 `o/r.git`로 파싱됩니다. 원본을 유지했습니다.
- reduced motion: 모든 성공 스텝이 이미 300ms보다 짧아 성공 총 시간은 줄지 않습니다. 롤백의 1,400ms 대기는 300ms로 줄어듭니다.
- JavaScript 타이머의 소수 ms 절삭으로 누적 시간에 작은 차이가 생깁니다. fake timer 검사는 이 차이를 고려해 ±50ms 이내로 검증합니다.
- CSS 최적화는 UI 색을 짧은 hex로 줄일 수 있습니다. 리더는 이를 지원하고, 꽃의 퍼센트 채널은 별도 변수로 보존해 hex 반올림을 방지했습니다.
- 체크박스는 원본 기본 여백과 light 색상 스킴을 명시해 Tailwind 초기화·페이지 dark 스킴 차이를 보정했습니다.
- 생성·정리가 반복되는 StrictMode에서는 canvas도 새로 만들어 해제된 WebGL 컨텍스트를 재사용하지 않습니다.

### 발견한 문제와 연결이 끊기는 지점

1. **실제 배포 호출 미구현**: 배포 생성 API는 DB의 queued 기록만 생성합니다. 호출 후 조회에서도 queued이며, `createDeployment`와 호출 경로에 빌더 요청 코드가 없습니다. 이 경계에서 실제 배포 흐름 검증을 중단했습니다. T26의 실행기 연결 후 다시 확인해야 합니다.
2. **배포 설정 입력 미지원**: branch·rootDir·targetPort·env를 포함한 등록 요청은 400입니다. 현재 API는 repo·name만 받습니다. Dockerfile 자동 생성, 비공개 레포 토큰, 헬스체크, 마이그레이션, Nginx 연결은 이번 프런트 흐름에서 검증하지 못했습니다.
3. **대시보드 목적지 미설정**: DASHBOARD_URL이 없고, 테스트로 성공 상태를 만든 프로젝트의 진입 API도 destination=null입니다. 꽃 진입 안내와 복귀만 확인했습니다.
4. **계정 화면 React 경고**: `src/app/account/page.tsx`에서 같은 부모의 AccountForm과 ProjectList에 동일한 user.id를 key로 지정합니다. 브라우저 콘솔에 중복 key 경고가 발생하며 개발 화면에 Issues 배지가 표시됩니다. 각 형제의 key를 구분해야 합니다. 확인한 페이지 흐름의 미처리 pageerror는 0개였지만 콘솔 경고는 존재합니다.
5. **메인 페이지 단위 테스트 실패**: 위 자동 검사 표의 server-only 모듈 로딩 실패를 수정해야 `pnpm test` 전체가 통과합니다.

별도 사용자 아이디와 이메일 인증 없는 가입은 계획 단계이며, 현재 구현은 여전히 이메일 인증이 필수입니다. 로컬 Mailpit 성공은 운영 SMTP 연결을 보장하지 않습니다.

- 생성한 테스트 계정과 그 계정에 종속된 프로젝트·배포·상태 이벤트, 테스트 인증·복구 메일을 삭제했습니다. 기존 계정·프로젝트·메일은 유지했습니다.
- 임시 테스트 스크립트·상세 체크 결과·스크린샷은 `/tmp/lily-check*`에 저장했습니다. 자격 증명은 결과 문서에 포함하지 않았습니다. 임시 파일은 영구 테스트 자산이 아닙니다.

- 정적 검사는 위 표의 명령으로 재현합니다. 런타임 검사는 테스트 계정 두 개를 만들고 메일 인증 후 등록·수정·타인 접근·중복 배포 요청을 반복합니다. 실제 배포 검증은 T26 연결 이후 빌더 ID·상태·배포 URL·헬스체크 결과까지 확인해야 합니다.

검증용 로컬 계정과 프로젝트/배포 기록은 삭제했습니다. 로그인 검증용 이메일 인증 상태와
배포 완료 기록은 로컬 fixture로 준비했습니다. 실제 빌드·운영 메일·클러스터 수집이 실행됐다는 의미는 아닙니다.
실서비스 URL/토큰·클러스터 접속 정보가 없어 운영 observer/cicd/nginx/DB 통합 검증은 남아 있습니다.

재현: README의 두 앱 실행 설정 적용 → 계정 로그인 → 내 프로젝트의 대시보드 버튼 →
미연결 안내 확인 → 내부 서비스 URL/토큰 설정 후 재시작 → 같은 프로젝트의 지표·로그·파드 확인.

## 2026-10-02 실제 클러스터 관측 연결

팀의 로컬 전체 배포 확인 후, SSH 터널을 통해 실행 중인 서비스에 프런트의 서버 전용
관측 설정을 연결했습니다. `lily-observer`와 `db-provisioner`는 각각 80번 포트로
Ready 상태였습니다. 배포된 `lily-blog-sample-e20072`에 대해 프런트의
`getMonitor()` 경로로 status·metrics·pods·logs·app·databases가 모두 `ready`를
반환했습니다. 파드는 2개, 로그는 80줄, 관리형 DB는 1개입니다. 최근 요청이 0건이라
observer의 상태 판정은 `HOLD`입니다. 이 값은 정상 판정이 아닙니다.

`lily-ingress` API Service는 현재 클러스터에 없어 route만 `unconfigured`입니다.
토큰과 터널 주소는 Git에서 제외된 `.env.local`에만 설정했습니다. 개발 서버를
재시작해 설정을 반영했습니다. 이 섹션은 위의 계약 응답 검사와 구분되는 실제
서비스 조회 결과입니다.
