# 로그인·회원가입과 사용자별 관리 계획

상태: **T13~T18 추가 — 구현 전**

## 1. 목표와 범위

사용자가 계정을 만들고 로그인해서 자신의 계정과 배포 프로젝트를 관리할 수 있게 합니다.
기존 랜딩·배포 시연·꽃술 확대는 유지하고, 실제 프로젝트의 대시보드 진입에는
로그인과 프로젝트 소유권 확인을 연결합니다.

### 포함

- 회원가입, 로그인, 로그인 유지, 로그아웃.
- 내 계정 조회와 표시 이름 수정.
- 이메일 인증·비밀번호 재설정 흐름(이메일·비밀번호 방식을 사용할 경우).
- 서버에 저장된 사용자별 프로젝트와 배포 기록의 연결.
- 로그인 상태에 따른 내비 표시와 보호된 경로·API 접근 처리.
- 배포 성공 → 로그인 확인 → 프로젝트 권한 확인 → 꽃술 확대 → 대시보드 연결.

### 별도 범위

- 대시보드 화면, 실제 배포 실행 엔진, 관리자용 전체 회원 관리.
- 소셜 로그인, 팀 공유·역할 관리, 계정 탈퇴·프로젝트 이전.

“사용자별 관리”는 우선 **본인 계정과 본인 프로젝트 관리**로 정의합니다.
관리자가 다른 회원을 관리하는 기능은 별도 요청에 따라 추가합니다.

## 2. 구현 전에 확정할 것 — T13

현재 저장소에는 인증 API·DB·인증 SDK가 없습니다. 다음 사항을 먼저 확정합니다.

| 항목 | 초안 / 확인할 내용 |
|---|---|
| 인증 서버 | 기존 백엔드 API가 있으면 해당 계약에 연결. 없으면 인증 서비스 또는 서버 구성을 선정 |
| 로그인 수단 | 초안은 이메일·비밀번호. 기존 서비스 방식이 있으면 우선 적용 |
| 계정 저장 | 서버 DB 또는 인증 서비스에 영속 저장 |
| 세션 | 서버가 검증하는 세션, 브라우저에는 HttpOnly 쿠키 사용을 기본안으로 검토 |
| 메일 | 인증 메일·비밀번호 재설정 메일 발송 주체와 개발 환경 처리 |
| 프로젝트 API | 프로젝트 ID, 소유자 ID, 실제 배포 완료 이벤트의 계약 |
| 대시보드 | 같은 앱의 경로인지 별도 앱인지, 두 앱이 사용하는 인증 주체와 로그인 전달 방식 |

백엔드 없이 로컬 저장소에 계정을 저장하는 기능은 실제 회원가입 완료로 취급하지 않습니다.
개발용 목업은 명시적으로 구분하고, 실제 계정·프로젝트 저장 완료와 별도로 기록합니다.
자체 인증 서버가 필요하면 프런트엔드 변경과 서버 작업의 담당 저장소를 함께 정합니다.

## 3. 사용자 흐름

### 회원가입과 로그인

1. 랜딩 내비의 “회원가입”에서 `/signup`으로 이동합니다.
2. 이메일·비밀번호·비밀번호 확인을 입력합니다. 표시 이름은 선택 항목으로 둡니다.
3. 프런트엔드가 입력 오류를 안내하고, 서버도 동일한 계약으로 검증합니다.
4. 계정은 서버에 생성합니다. 인증 메일이 필요한 방식이면 인증 안내를 표시합니다.
5. 이메일 인증과 로그인이 끝나면 원래 방문하려던 내부 경로 또는 랜딩으로 이동합니다.
6. 로그인 후 내비에는 “내 계정”과 “로그아웃”을 표시합니다.

중복 제출·네트워크 오류·잘못된 인증 정보·이메일 미인증·만료된 링크를 각각 안내합니다.
구체적인 비밀번호 정책과 회원가입 후 자동 로그인 여부는 T13의 서버 계약을 따릅니다.
이메일 인증은 이메일 소유 확인이며 GitHub 저장소 접근 권한을 부여하지 않습니다.

### 내 계정

- `/account`에서 이메일·표시 이름·인증 상태를 확인합니다.
- 표시 이름 수정은 서버에 저장하고, 새로고침 후에도 유지합니다.
- 비밀번호 변경·재설정은 선정한 인증 시스템의 절차를 사용합니다.
- 로그아웃은 서버 세션을 무효화하고 화면의 사용자·프로젝트 캐시도 비웁니다.
- 세션 만료 시 다시 로그인하도록 안내합니다. 다른 계정으로 로그인했을 때
  이전 계정의 프로젝트나 배포 상태가 남지 않게 합니다.

### 프로젝트와 꽃 진입

- 공개 랜딩의 배포 시연은 로그인 없이도 사용할 수 있습니다.
- 현재 시연의 `DeployResult`에는 서버 프로젝트 ID나 실제 소유권이 없습니다.
  시연 성공만으로 실제 계정에 프로젝트를 생성하거나 대시보드 접근 권한을 주지 않습니다.
- 실제 프로젝트 등록·배포 기록 저장은 로그인한 사용자에 연결합니다.
- 실제 배포가 성공한 프로젝트에서만 대시보드 진입을 허용합니다.
- 미로그인이라면 확대를 시작하기 전에 로그인 페이지로 보냅니다.
  복귀 목적지는 허용한 내부 경로·서버 프로젝트 ID로 구성합니다.
- 로그인 후 서버에서 프로젝트 소유권과 배포 상태를 다시 조회합니다.
  클라이언트가 넘긴 성공 상태나 `ownerId`를 권한 판단에 사용하지 않습니다.
- 프로젝트가 여전히 유효하고 사용자에게 권한이 있으면 꽃술 확대와
  `onEnterDashboard` 연결을 실행합니다. 타인 프로젝트·삭제된 프로젝트는 진입을 막습니다.
- 실제 프로젝트 API·대시보드 목적지가 연결되기 전에는 현재 “연결 준비 중” 동작을 유지합니다.

## 4. 인증과 권한 구조

인증 상태는 계정 표시용으로 클라이언트에 전달하지만, 계정 조회·수정·프로젝트 조회·
진입 권한의 최종 확인은 서버에서 수행합니다.

- 세션 읽기와 인증 서비스 호출을 `lib/auth`의 서버 모듈에 모읍니다.
- 로그인·회원가입 폼은 Client Component, 보호된 데이터 조회는 서버에서 처리합니다.
- 프런트엔드 API 경계가 필요하면 Route Handler 또는 Server Action을 사용합니다.
  기존 백엔드가 있으면 인증 시스템을 중복 구현하지 않습니다.
- 세션 쿠키의 HttpOnly·Secure(운영 HTTPS)·SameSite·만료 정책과 로그아웃 처리를
  인증 시스템에 맞춰 정합니다. 세션·비밀번호를 localStorage에 저장하지 않습니다.
- 비밀번호 저장·해시, 로그인 시도 제한, 쿠키 기반 변경 요청의 CSRF 처리는
  인증 서버 또는 선정한 인증 라이브러리에서 담당하며 계약에 포함합니다.
- 화면·내비·경로 가드는 사용자 경험을 위한 처리입니다. 각 데이터 조회·변경 지점에서도
  세션과 소유권을 확인합니다. Proxy만으로 접근 권한 검사를 끝내지 않습니다.
- 반환 데이터에서 비밀번호 해시·세션 비밀값을 제외합니다.
- 사용자별 데이터가 공용 캐시에 섞이지 않도록 캐시 정책을 구분합니다.
- `next` 복귀 경로는 허용한 내부 경로만 사용합니다.

이 구조는 [Next.js 인증 가이드](https://nextjs.org/docs/app/guides/authentication)의
서버 세션·데이터 접근 권한 검사 지침을 기준으로 합니다.
구현 시 설치된 Next.js 16.3.7의 인증·`cookies()` 문서를 다시 확인합니다.

## 5. 사용자와 프로젝트 연결

서버 데이터 계약의 초안이며, 실제 모델·필드명은 기존 API에 맞춥니다.

| 데이터 | 주요 필드 | 관리 주체 |
|---|---|---|
| 사용자 | `id`, `email`, `displayName`, `emailVerified` | 인증 서버 |
| 세션 | 사용자 연결, 만료·무효화 정보 | 인증 서버 / 인증 서비스 |
| 프로젝트 | `id`, `ownerId`, `repo`, `name` | 프로젝트 서버 |
| 배포 기록 | `id`, `projectId`, `status`, `finishedAt` | 프로젝트 / 배포 서버 |

`ownerId`는 서버가 로그인 세션에서 결정합니다. 목록 조회는 해당 사용자 프로젝트만 반환하고,
상세 조회·변경은 매번 프로젝트 소유권을 확인합니다. 프로젝트 생성·배포 기록 저장의
중복 요청 처리도 서버 계약에 포함합니다. `slug`는 표시용이며 권한 식별자로 사용하지 않습니다.

현재 [DASHBOARD.md](./DASHBOARD.md)의 `DashboardEntry.result`는 시연 결과입니다.
T18에서 실제 연결을 추가할 때 서버 프로젝트 ID를 포함하는 진입 데이터로 확장하되,
확대 연출과 인증·프로젝트 처리는 서로 분리합니다.

인증 방식이 확정되면 필요한 파일만 생성하고, 쓰지 않는 계층이나 빈 라우트를 미리 만들지 않습니다.

## 7. 확인 기준

- 회원가입한 계정이 서버에 저장되고 다른 브라우저에서도 로그인 가능함.
- 로그인 오류·이메일 인증·만료된 복구 링크를 처리함.
- 새로고침·세션 만료·로그아웃 후 상태가 올바르게 반영됨.
- 계정 A와 B의 프로젝트가 섞이지 않고, B가 A의 프로젝트 ID로 접근해도 서버가 거부함.
- 로그아웃·계정 변경 후 이전 사용자 캐시와 랜딩 배포 상태가 남지 않음.
- 성공한 본인 프로젝트만 꽃 진입을 허용하고, 실제 API가 없는 시연 결과에 권한을 부여하지 않음.
- 기존 꽃 연출·폼·모바일 레이아웃을 유지함.

자동 테스트 추가·실행은 별도 요청이 있을 때 진행합니다.
실제 인증·프로젝트 서버에 연결되기 전에는 계정 관리 구현 완료로 표시하지 않습니다.
